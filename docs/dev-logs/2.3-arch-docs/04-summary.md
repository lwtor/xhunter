## 二、关键决策记录

### 决策 1：双视角文档策略

> 文档要写"当前真实状态"还是"目标蓝图"？

**选择：双视角并存（当前快照 + 目标蓝图 + 演进路线）**

理由：
- 纯快照：每加一个模块就要大改，且看不到全貌
- 纯蓝图：当前找不到对应代码，新人困惑
- 双视角：能对照代码学习，又能预见未来路径

落地：两份文档都分三段——「当前快照」「目标蓝图」「演进路线」。

### 决策 2：快照机制

> 怎么避免文档与代码渐行渐远？

**做法：**
1. 文档顶部标 `📌 快照截止步骤：X.Y`
2. 后续每次拆模块（如 3.1 引入 feature-explore）时，把"更新这两份文档"作为该步骤阶段 E 的必做项
3. 当前快照标记前移 + 演进路线条目改为"已完成"

这样既能避免每次小改都回头补全部模块，又能避免文档腐化。

### 决策 3：两份文档分工

> 思想 + 工程合并成一份还是分开？

**选择：分开两份，互相交叉引用**

| 文档 | 定位 | 内容 |
| --- | --- | --- |
| `ARCHITECTURE.md` | 思想层 | 架构定位 / KMP 心智 / MVI 数据流 / Clean 分层 / 6 项决策卡（D1~D6） |
| `MODULES.md` | 工程层 | settings.gradle.kts 模块清单 / 模块依赖 Mermaid 图 / 每模块卡片（职责/依赖/关键文件）/ 新增模块 6 步 checklist |

两份文档互相交叉引用 ≥ 4 处，方便读者按需跳转。

## 三、学到的东西

### 文档维护的工程化思维

学习项目最大的隐性成本不是写代码，而是**写完代码后回看时认不出来**。本步建立的"双视角 + 快照机制 + 阶段 E 强制更新"，本质上是把"文档维护"也工程化——和单元测试一样，每次代码改动都有一个明确的"配套动作"。

### 模块依赖图的真正价值

Mermaid 图本身只是表达手段，关键是它**强制思考"谁依赖谁"**。当我把 `feature` / `domain` / `data` / `core` 画成 Mermaid 时，自动暴露了几个之前没想清楚的问题：
- 跨 feature 通信走哪里？→ 答案是 domain UseCase 或导航参数（写进了 ARCHITECTURE 铁律段）
- expect/actual 集中在哪一层？→ 答案是 core-* 的固定 API 边界（写进了 KMP 心智段）

这些隐性约定写下来，比"靠经验"可靠得多。

### 演进路线表的妙用

把目标蓝图全模块按"引入步骤"排序，做成一张演进路线表，等于给项目装了一根**时间轴**：
- 每完成一步，对应模块行打 ✅
- 看不懂某个模块为什么存在 → 跳到那一步的归档目录看 spec
- 想跳过某个模块 → 一眼看出会影响后续哪些模块

这张表的成本只有十几行 Markdown，但承担了"项目记忆"的功能。
